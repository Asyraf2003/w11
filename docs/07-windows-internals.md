# Advanced Windows interfaces and less visible capabilities

Official sources checked 2026-11-08. This is a capability reference, not an instruction to enable, tune, install, or migrate anything.

Every table entry below is `DOCUMENTED`; applicability or active use on this UM3406GA remains `UNKNOWN` unless the runtime evidence register says otherwise. An API being part of Windows, a service existing, and a workload using it are different claims. Example queries are read-only discovery examples, not a record that they succeeded here. Some require elevation or an installed module; access denied is an evidence gap.

## Native application and management interfaces

| Capability | Behavior / useful inspection | Dependencies and limits | Official evidence |
|---|---|---|---|
| Win32 | Native process, window, input, file, memory, device, and synchronization interfaces. 64-bit applications also use the platform traditionally called Win32. | A documented OS API does not grant unrestricted hardware access; device handles, ACLs, driver contracts, architecture and OS versions still apply. | [Win32 desktop platform](https://learn.microsoft.com/en-us/windows/win32/desktop-programming) |
| Windows Runtime / WinRT | Typed `Windows.*` interfaces expose areas including media capture, notifications, storage and device access across language projections. | API contracts, package identity, manifest capabilities, consent, and desktop-app restrictions vary by API. WinRT is an ABI, not evidence of an installed UWP app using it. | [WinRT API reference](https://learn.microsoft.com/en-us/uwp/), [desktop interop](https://learn.microsoft.com/en-us/windows/apps/develop/interop/) |
| COM and OLE | Binary interfaces connect shell extensions, media components, automation and many management APIs; OLE also supports compound-document/data-transfer scenarios. | Registration, process bitness, apartment/threading model, activation permissions and component installation matter. DCOM is a distinct remote surface with separate controls. | [COM](https://learn.microsoft.com/windows/win32/com/) |
| Windows SDK versus Windows App SDK | Windows SDK describes OS interfaces; Windows App SDK delivers app-platform features on its own release cycle. | Having a new app SDK does not upgrade every underlying OS or driver capability. | [Windows developer FAQ](https://learn.microsoft.com/en-us/windows/apps/get-started/windows-developer-faq) |
| PowerShell object interfaces | Native modules provide structured inventory of devices, packages, networking, storage and system state. `Get-Command -Name Get-PnpDevice,Get-CimInstance,Get-AppxPackage -ErrorAction SilentlyContinue` checks command exposure. | Windows PowerShell 5.1 and separately installed PowerShell 7 differ in module compatibility. A script execution-policy error does not prove a Windows capability absent. | [CIM cmdlet](https://learn.microsoft.com/en-us/powershell/module/cimcmdlets/get-ciminstance), [supported versus removed engines](https://learn.microsoft.com/en-us/windows/whats-new/removed-features) |
| WMI / CIM | Providers expose hardware, firmware, operating-system and management data. Example: `Get-CimInstance Win32_Processor -Property Name,NumberOfCores,NumberOfLogicalProcessors`. | Local CIM queries normally use WMI/COM; remote sessions add transport and authentication requirements. Provider-reported values can be incomplete or misleading. | [WMI](https://learn.microsoft.com/en-us/windows/win32/wmisdk/wmi-start-page), [Get-CimInstance](https://learn.microsoft.com/en-us/powershell/module/cimcmdlets/get-ciminstance) |
| IPC | Named pipes, shared/file-mapped memory, RPC, COM and other mechanisms allow processes to exchange data. | An IPC name or listening endpoint is not a supported public automation API. Security descriptors and protocol ownership apply. | [Interprocess communication](https://learn.microsoft.com/en-us/windows/win32/ipc/interprocess-communications) |
| UI Automation | Accessibility providers expose semantic UI elements to assistive tools and test clients. | Apps must supply usable providers; custom canvases, privilege boundaries and protected desktops can limit coverage. It is distinct from image recognition and raw key injection. | [UI Automation](https://learn.microsoft.com/en-us/windows/win32/winauto/entry-uiauto-win32) |

## Devices, firmware, and driver layers

| Capability | Behavior / useful inspection | Dependencies and limits | Official evidence |
|---|---|---|---|
| PnP device tree | Windows enumerates devices, parent/child relationships, interfaces, status, IDs and bound drivers. `pnputil /enum-devices /connected` inspects connected devnodes. | A devnode can be virtual, composite, software-only or a child function. A disconnected entry is not proof that physical hardware is currently installed. | [PnPUtil enumeration](https://learn.microsoft.com/en-us/windows-hardware/drivers/devtest/pnputil-command-syntax) |
| Driver Store versus active binding | `pnputil /enum-drivers` lists third-party packages; newer builds also expose tree, class, stack and matching-driver information. | A stored INF is not proof that its driver is active. Rank, device matching, extension packages and the active devnode binding matter; compare packages within their actual driver family. | [PnPUtil syntax and version gates](https://learn.microsoft.com/en-us/windows-hardware/drivers/devtest/pnputil-command-syntax) |
| Filter and extension drivers | Upper/lower filters and extension INFs add OEM behavior around a function driver. Device-stack inspection can separate generic HID/audio layers from ASUS, Realtek, Cirrus or other extensions. | A service name cannot establish the full data path or the effect currently selected by an app. Do not export proprietary binaries as public evidence. | [PnPUtil device stack/driver inspection](https://learn.microsoft.com/en-us/windows-hardware/drivers/devtest/pnputil-command-syntax) |
| ACPI | `Acpi.sys` interprets the firmware namespace and participates in device enumeration, resource and power management. | OEM ACPI topology/methods are platform-specific. Windows exposure does not prove that Linux exposes an equivalent control, nor that writing a guessed WMI method is safe. | [Windows ACPI driver](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/acpi-driver) |
| Firmware identity | CIM BIOS/baseboard model and version fields preserve a platform reference without extracting firmware images. | Version/date/model are enough for a public baseline. Omit serial numbers, UUIDs, ownership tags, boot secrets and full firmware-variable dumps. | [CIM query interface](https://learn.microsoft.com/en-us/powershell/module/cimcmdlets/get-ciminstance), [ACPI responsibility boundary](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/acpi-driver) |
| Firmware table / UEFI variable APIs | `GetSystemFirmwareTable` exposes specified ACPI/SMBIOS tables; `GetFirmwareEnvironmentVariable` reads named firmware variables. | Platform and privileges constrain access. Tables can contain unique identifiers, and variables can contain sensitive security state. This inventory records the API contract without dumping them. | [Firmware table API](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-getsystemfirmwaretable), [firmware variable API](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfirmwareenvironmentvariablea) |
| Sensor APIs | Windows interfaces expose light, orientation, motion and other sensors when drivers/hardware provide them. | A sensor-hub devnode does not prove that every sensor type is present or that an app can obtain a reading. OEM automatic keyboard brightness can use a different internal path. | [Windows sensor interfaces](https://learn.microsoft.com/en-us/windows/apps/develop/devices-sensors/sensors) |
| USB4 connection manager | Windows 11 manages USB4 domains, routers, protocol tunnels, bandwidth and power. Host and device-router drivers are distinct. | Requires actual USB4 hardware, firmware and suitable cables/devices. Router presence does not prove a dock, external GPU, maximum link rate or every tunnel has worked. | [USB4 connection manager](https://learn.microsoft.com/en-us/windows-hardware/design/component-guidelines/usb4-intro-to-connection-manager) |
| USB4 networking / USB4NET | Two compatible PCs connected by a suitable cable can enumerate a peer-to-peer network adapter, allowing ordinary network file sharing. | This is Ethernet over a USB4 interdomain connection. Sharing permissions still apply. Connecting two ports on one PC does not create a useful peer network. | [USB4 interdomain connections](https://learn.microsoft.com/en-us/windows-hardware/design/component-guidelines/usb4-interdomain-connections) |
| USB4 sleep / wake relations | Tunneled PCIe, USB and display devices participate in host-router power management. | Firmware port mappings and device/driver cooperation affect real sleep and resume behavior. Enumeration cannot establish low idle power or reliable dock wake. | [USB4 power requirements](https://learn.microsoft.com/en-us/windows-hardware/design/component-guidelines/usb4-power-management-requirements) |

|---|---|---|---|

| Modern Standby | S0 low-power idle offers fast on/off transitions with controlled background activity and possible connectivity. | Firmware support is required. “Network connected” does not promise every desktop app runs continuously or establish low overnight drain. Measure behavior separately. | [Modern Standby model](https://learn.microsoft.com/en-us/windows-hardware/design/device-experiences/modern-standby) |

| VBS and memory integrity / HVCI | Uses virtualization isolation for code-integrity protection. `Get-CimInstance -Namespace root\Microsoft\Windows\DeviceGuard -ClassName Win32_DeviceGuard` exposes security-state properties. | Hardware support, enabled/configured state and running state are distinct. | System Guard Secure Launch / SMM protection | Adds startup/firmware-related protections on supported hardware. | Secure Boot being on does not prove Secure Launch, DRTM or SMM protection is operating. | BitLocker / device encryption | Encrypts storage volumes; some qualifying consumer systems expose automatic device encryption, while full management depends on edition. | Encryption status is distinct from key custody and recovery readiness. | Windows Hello / FIDO | PIN/biometric sign-in and supported website authentication can use device-bound credentials. | Hello face requires appropriate IR hardware; normal RGB camera presence is insufficient. Do not inspect biometric templates or enrollment secrets. | [Windows Hello distinctions](https://learn.microsoft.com/en-us/windows/security/identity-protection/hello-for-business/) |
| DPAPI | Apps can protect blobs tied to user/machine context. | Encrypted files copied to another OS are not automatically decryptable. This documents a dependency, not permission to extract credentials or DPAPI material. | [CryptProtectData contract](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata) |
| CNG | Extensible cryptographic algorithm and key-storage provider interfaces serve native applications. | Software, TPM and other providers have different capabilities and access controls. Algorithm presence does not prove an application selected hardware-backed storage. | [Cryptography API: Next Generation](https://learn.microsoft.com/en-us/windows/win32/seccng/cng-portal) |
| Application control | App Control and AppLocker provide policy-driven executable/script trust controls. | Rule capabilities, deployment/licensing and policy state differ; installed management components do not prove an enforcement policy. | [Application control reference](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/app-control-for-business/) |

## Lifecycle and inference boundaries worth preserving

| Topic | Preserved distinction | Evidence |
|---|---|---|
| WMIC versus WMI | Microsoft's current removal list records WMIC removed on Windows 11 24H2+ and no longer a Feature on Demand as of August 2026. This affects the old executable, not WMI/CIM.
